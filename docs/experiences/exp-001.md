# EXP-001 — Redondance relationnelle vs répétition

> **Question : à budget d'inférence comparable, des vues reliées par des contraintes explicites permettent-elles de détecter les erreurs d'une production LLM mieux que de simples répétitions indépendantes de la même question ?**

**Statut :** protocole expérimental pré-enregistré  
**Projet :** Elenchos  
**Hypothèse testée :** H1 — détection  
**Langue :** français  
**Date :** août 2026

---

## 1. But de l'expérience

EXP-001 est volontairement minimal.

Il ne cherche pas à démontrer qu'un « code correcteur pour LLM » existe.

Il teste une proposition beaucoup plus faible :

> **à quantité de génération comparable, remplacer une partie de la répétition brute par des vues structurellement reliées apporte-t-il davantage d'information sur le fait que la réponse principale soit erronée ?**

Si cette hypothèse échoue déjà dans un domaine simple et contrôlé, il faudra fortement réviser l'intuition d'Elenchos avant de poursuivre vers la localisation ou la correction.

---

## 2. Ce que l'expérience ne teste pas

EXP-001 ne teste pas :

- la correction d'une réponse ;
- la localisation de l'erreur ;
- un système multi-agent complexe ;
- le débat entre modèles ;
- un vérificateur LLM ;
- une généralisation aux questions ouvertes ;
- l'existence d'une métrique sémantique analogue à la distance de Hamming ;
- l'existence d'un véritable code correcteur au sens mathématique.

Les hypothèses H2 et H3 de la formalisation restent hors périmètre.

---

## 3. Principe expérimental

On considère une question `x` et une production principale :

```text
y0 = A(x)
```

L'expérimentateur connaît la vérité terrain pour déterminer :

```text
Correct(x, y0)
```

Mais **le protocole de détection n'a jamais accès à cette vérité terrain**.

Deux détecteurs utilisent ensuite le même nombre total d'appels au modèle.

### Détecteur R — répétition

Il repose uniquement sur plusieurs réponses à la question originale.

```text
x ──→ y0
x ──→ y1
x ──→ y2
x ──→ y3
```

La divergence entre les répétitions fournit le signal d'incertitude.

### Détecteur E — Elenchos

Il conserve la même production principale `y0`, mais remplace les répétitions supplémentaires par des vues transformées :

```text
x      ──→ y0
T1(x)  ──→ y1
T2(x)  ──→ y2
T3(x)  ──→ y3
```

Des relations attendues entre `y0`, `y1`, `y2` et `y3` produisent un **syndrome élénctique**.

L'expérience compare la capacité de ces deux signaux à prédire que `y0` est faux.

---

## 4. Domaine choisi

Le premier domaine est l'**arithmétique entière exacte**.

Ce choix est méthodologique, pas applicatif.

Il permet de disposer :

- d'une vérité terrain incontestable pour l'évaluation ;
- de sorties simples à parser ;
- de transformations valides par construction ;
- de contraintes déterministes ;
- d'une difficulté paramétrable ;
- d'aucun besoin de juge LLM.

EXP-001 doit éviter les problèmes textuels et les réponses argumentées afin de ne pas introduire prématurément l'extraction faillible de claims.

---

## 5. Famille de tâches initiale

Une instance principale est une addition entière :

```text
x(a,b) := « Calculer exactement a + b. Répondre uniquement par l'entier résultat. »
```

avec :

```text
a, b ∈ Z
```

Les nombres seront générés automatiquement dans des bandes de difficulté définies avant l'évaluation finale.

L'objectif n'est pas de tester si un modèle sait additionner en général, mais d'obtenir un taux d'erreur non nul permettant d'évaluer un détecteur.

---

## 6. Calibration de difficulté

Un **jeu pilote**, distinct du jeu d'évaluation, servira uniquement à choisir une bande de difficulté raisonnable.

Cible souhaitée pour la production principale :

```text
5 % ≤ taux d'erreur ≤ 40 %
```

Pourquoi :

- en dessous de 5 %, trop peu d'erreurs sont disponibles pour mesurer correctement le détecteur ;
- au-dessus de 40 %, on risque d'étudier un modèle essentiellement incapable de réaliser la tâche plutôt qu'un mécanisme de détection d'erreur.

Les données du pilote ne devront jamais être réutilisées pour les résultats principaux.

Une fois la bande de difficulté choisie, elle est gelée avant l'exécution de l'évaluation.

---

## 7. Transformations Elenchos

Pour chaque instance `(a,b)`, trois transformations sont utilisées.

### T1 — Commutativité

```text
T_comm(a,b) = (b,a)
```

Relation attendue :

```text
y_comm = y0
```

Violation :

```text
z_comm = 1 si y_comm ≠ y0
```

---

### T2 — Conservation par translation opposée

On choisit un entier non nul `k` selon une distribution fixée avant l'expérience.

```text
T_offset(a,b,k) = (a+k, b-k)
```

Puisque :

```text
(a+k) + (b-k) = a+b
```

la relation attendue est :

```text
y_offset = y0
```

Violation :

```text
z_offset = 1 si y_offset ≠ y0
```

---

### T3 — Homogénéité par facteur entier

On choisit un multiplicateur entier `m`, avec `m ∉ {-1,0,1}`.

```text
T_scale(a,b,m) = (ma, mb)
```

Relation attendue :

```text
y_scale = m × y0
```

Violation :

```text
z_scale = 1 si y_scale ≠ m × y0
```

Le calcul de `m × y0` est effectué par le vérificateur déterministe du protocole.

Il vérifie uniquement la relation entre deux productions ; il ne calcule pas directement `a+b` pour décider si `y0` est correct.

---

## 8. Oracle blindness

Dans ce domaine, un programme capable de vérifier les relations serait évidemment aussi capable de calculer directement `a+b`.

L'absence d'oracle est donc ici une **contrainte d'interface expérimentale**, pas une impossibilité computationnelle.

Le protocole Elenchos reçoit uniquement :

```text
- les productions y0, y_comm, y_offset, y_scale ;
- les paramètres des transformations nécessaires à leurs relations ;
- les règles de contrainte.
```

Il ne reçoit jamais :

```text
truth = a+b
```

Le composant d'évaluation, séparé du détecteur, est le seul à calculer la vérité terrain.

Cette séparation devra être matérialisée dans l'implémentation et testée.

---

## 9. Syndrome élénctique EXP-001

Le syndrome est le vecteur :

```text
S = (z_comm, z_offset, z_scale)
```

avec :

```text
z_i ∈ {0,1}
```

Exemples :

```text
S = (0,0,0)  aucune violation observée
S = (1,0,0)  violation de commutativité observée
S = (1,1,0)  deux contraintes violées
S = (1,1,1)  toutes les contraintes violées
```

Pour H1, on n'interprète pas encore la forme précise du syndrome.

On utilise seulement un score de détection simple :

```text
score_E = (z_comm + z_offset + z_scale) / 3
```

L'analyse détaillée des motifs de syndrome relève de H2 et reste exploratoire.

---

## 10. Baseline de répétition

Le détecteur R effectue quatre générations de la question originale :

```text
x → y0
x → y1
x → y2
x → y3
```

Il mesure la divergence avec la production principale :

```text
d_i = 1 si yi ≠ y0
```

Le score baseline est :

```text
score_R = (d1 + d2 + d3) / 3
```

Ainsi :

```text
R : 1 production principale + 3 répétitions
E : 1 production principale + 3 vues structurées
```

Les deux protocoles utilisent exactement quatre appels modèle par instance.

---

## 11. Budget comparable

Le nombre d'appels est identique, mais cela ne garantit pas un coût strictement identique en tokens.

L'expérience enregistrera donc pour chaque protocole :

- nombre d'appels ;
- tokens d'entrée ;
- tokens de sortie ;
- latence ;
- coût monétaire éventuel ;
- modèle et paramètres d'inférence.

Le résultat principal sera présenté à nombre d'appels égal.

Une analyse secondaire rapportera les performances normalisées par coût en tokens.

---

## 12. Conditions d'inférence

Pour un modèle donné, les paramètres doivent être gelés avant l'évaluation :

- modèle exact ;
- version si disponible ;
- température ;
- top-p ;
- seed si le fournisseur la supporte réellement ;
- limite de tokens ;
- prompt système éventuel ;
- format demandé.

Aucun changement de prompt ne sera effectué après observation des résultats du jeu d'évaluation.

Toute optimisation de prompt doit être réalisée uniquement sur le jeu pilote.

---

## 13. Parsing des réponses

Le modèle reçoit l'instruction de répondre uniquement par un entier.

Le parseur accepte :

```text
^-?[0-9]+$
```

après suppression des espaces périphériques.

Une réponse non parsable est considérée comme :

```text
production invalide
```

Pour l'évaluation de `y0`, une production invalide est incorrecte.

Pour une vue secondaire, une production invalide produit une violation de la contrainte correspondante.

Les erreurs de format ne doivent pas être silencieusement corrigées par un autre LLM.

---

## 14. Génération du jeu d'évaluation

Le générateur doit être déterministe à partir d'une seed publiée avec les résultats.

Les instances doivent éviter :

- les doublons ;
- les valeurs déjà présentes dans le pilote ;
- des transformations produisant exactement l'instance originale ;
- `k = 0` ;
- `m ∈ {-1,0,1}` ;
- les débordements du type numérique choisi côté implémentation.

Les distributions de `a`, `b`, `k` et `m` seront enregistrées dans le manifeste de l'expérience.

---

## 15. Taille d'échantillon

Deux niveaux sont prévus.

### Smoke test

```text
N = 100 instances
```

But : valider l'implémentation, le parsing, les métriques et l'absence de fuite d'oracle.

Les résultats du smoke test ne doivent pas être utilisés pour conclure sur H1.

### Évaluation principale

Cible :

```text
N ≥ 1000 instances par configuration de modèle
```

Si le coût d'inférence rend cette cible irréaliste, la taille finale devra être décidée **avant** l'examen des résultats principaux et documentée explicitement.

---

## 16. Variable cible

Pour chaque instance :

```text
error0 = 1 - Correct(x,y0)
```

Le détecteur doit prédire `error0`.

Les scores comparés sont :

```text
score_R
score_E
```

La vérité terrain est utilisée uniquement pour mesurer leur pouvoir discriminant.

---

## 17. Métriques principales

### Métrique primaire

```text
AUROC(score, error0)
```

On compare :

```text
AUROC_E - AUROC_R
```

### Métriques secondaires

- AUPRC ;
- précision ;
- rappel ;
- F1 à seuil fixé ;
- rappel à taux de faux positifs fixé ;
- calibration si un score probabiliste est ajouté ultérieurement ;
- risk-coverage curve ;
- erreur résiduelle à 80 % de couverture ;
- coût moyen par instance.

---

## 18. Abstention et risk-coverage

Un usage naturel d'un détecteur est d'accepter les productions à faible score et de s'abstenir sur les plus suspectes.

Pour un seuil `τ` :

```text
accepter si score < τ
s'abstenir sinon
```

On mesure :

```text
coverage(τ) = fraction des productions acceptées
```

et :

```text
risk(τ) = taux d'erreur parmi les productions acceptées
```

Une bonne détection doit permettre de réduire le risque lorsqu'on accepte de diminuer la couverture.

---

## 19. Test statistique

La comparaison principale utilisera un bootstrap apparié par instance.

Pour chaque réplication bootstrap :

1. rééchantillonner les instances avec remise ;
2. calculer `AUROC_E` ;
3. calculer `AUROC_R` ;
4. calculer `Δ = AUROC_E - AUROC_R`.

On rapportera :

```text
ΔAUROC
IC bootstrap 95 %
```

Les deux détecteurs étant évalués sur les mêmes instances, l'appariement doit être conservé.

---

## 20. Critère de soutien de H1

H1 sera considérée **soutenue dans le domaine EXP-001** si :

```text
ΔAUROC > 0
```

et si l'intervalle de confiance bootstrap à 95 % de `ΔAUROC` n'inclut pas zéro.

On distinguera toutefois signification statistique et intérêt pratique.

Un effet sera qualifié de **pratiquement notable** si :

```text
ΔAUROC ≥ 0,05
```

Ce seuil pratique est conventionnel et devra être signalé comme tel.

---

## 21. Critères de réfutation ou d'échec

EXP-001 constitue un résultat négatif pertinent si :

- `AUROC_E` n'est pas supérieure à `AUROC_R` ;
- l'intervalle de confiance de `ΔAUROC` reste compatible avec zéro ;
- les vues structurées échouent aussi souvent de manière corrélée que les répétitions ;
- la structure n'apporte un gain qu'au prix d'un coût disproportionné ;
- les transformations augmentent artificiellement la difficulté et dégradent le signal ;
- le résultat disparaît dès qu'on change légèrement la bande de difficulté.

Un résultat négatif ne devra pas être reformulé comme une réussite en changeant a posteriori de métrique principale.

---

## 22. Analyse des erreurs corrélées

EXP-001 doit enregistrer la fréquence des cas suivants :

```text
y0 faux + syndrome nul
```

Ce sont les **erreurs non détectées** les plus importantes pour Elenchos.

Exemple :

```text
x        → 94
T_comm   → 94
T_offset → 94
T_scale  → 188   avec m=2
```

Le syndrome est parfaitement cohérent :

```text
S = (0,0,0)
```

alors que la réponse principale peut être fausse.

Ces cas représentent l'équivalent conceptuel d'une erreur qui reste dans l'espace des contraintes observées.

Ils doivent être conservés et analysés, pas masqués.

Sans tester formellement H2, on peut enregistrer la distribution :

```text

```

et les huit syndromes possibles :

```text

100

110

```

Cette analyse est strictement exploratoire dans EXP-001.

Elle pourra servir à concevoir une future expérience H2, mais ne doit pas être utilisée pour modifier rétroactivement le score principal.

## 24. Contrôles négatifs

Au moins un contrôle négatif doit être prévu.

Exemple : remplacer une transformation structurée par une simple reformulation syntaxique sans invariant nouveau.

But : vérifier qu'un éventuel gain vient de la **relation structurée** et non seulement du fait d'avoir modifié le prompt.

Ce contrôle peut être exécuté après le protocole principal mais doit être défini avant l'analyse finale.

---

## 25. Menaces à la validité

### Tâche trop simple

Un modèle presque parfait rend le détecteur impossible à évaluer.

### Tâche trop difficile

Un modèle massivement faux peut produire des erreurs systématiques qui satisfont toutes les contraintes.

### Transformations de difficulté inégale

`T_scale` peut être plus difficile que la question originale et créer des violations qui signalent surtout sa propre difficulté.

### Dépendance au modèle

Un gain sur un modèle ne démontre pas un mécanisme général.

### Dépendance au prompt

Les formulations peuvent modifier fortement le comportement.

### Vérificateur trop puissant

Dans un domaine fermé, le vérificateur pourrait calculer directement la réponse. L'interface doit donc empêcher explicitement cette fuite.

### Corrélation des erreurs

Des transformations structurelles ne garantissent aucune indépendance effective.

## 28. Séparation protocole / implémentation

Ce document définit **ce qui doit être testé**.

Il ne prescrit pas encore l'architecture logicielle détaillée.

L'implémentation devra être aussi petite que possible et ne pas introduire un framework général prématuré.

Le premier code n'a besoin que de :


## 29. Interprétation possible des résultats

### Cas A — Elenchos nettement supérieur

Cela fournirait un premier indice que :

> la structure relationnelle apporte de l'information au-delà de la simple répétition.

Cela justifierait une réplication sur d'autres transformations, modèles et domaines.

Cela **ne démontrerait pas** l'existence d'un code correcteur général.

### Cas B — performances équivalentes

La structure choisie n'apporte pas plus d'information que la répétition brute.

Il faudrait déterminer si :

- l'intuition est mauvaise ;
- les transformations sont mauvaises ;
- ou les erreurs restent trop corrélées.

### Cas C — Elenchos inférieur

Résultat particulièrement instructif.

Les transformations peuvent introduire plus de bruit qu'elles n'apportent de contrainte utile.

Cela constituerait une réfutation directe de la version naïve de H1 pour ce domaine.

## 30. Condition avant de passer à EXP-002

Aucune expérience de localisation ou de correction ne doit être lancée simplement parce qu'EXP-001 est terminé.

La question préalable est :

> **avons-nous observé un signal reproductible montrant que la structure relationnelle apporte de l'information sur l'erreur ?**

Si non, H2 et Diorthosis restent prématurées.

Si oui, EXP-002 pourra chercher à déterminer si **la forme du syndrome** contient davantage d'information que son simple poids.

## 32. Hypothèse pré-enregistrée

> **H1 — Pour une tâche d'arithmétique entière contrôlée, à quatre appels modèle par instance, le score dérivé de trois contraintes relationnelles explicites distinguera mieux les productions principales correctes des productions principales incorrectes qu'un score dérivé de trois répétitions indépendantes de la question originale.**

Cette hypothèse est celle qu'EXP-001 doit essayer de réfuter.
